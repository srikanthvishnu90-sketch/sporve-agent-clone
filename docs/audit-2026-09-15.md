# Audit — 2026-09-15 (executed 2026-09-16 against `main` 5546cca and the live project `tseszaprvtvqrkfpditu`)

Read-only. Nothing was changed. Every finding names its evidence: a file and line on `main`, a live query result, or a row count. **Repo** means a file on `main`; **live** means the production database. They differ, because every migration in the `20260915_0010xx` block (001050–001066) is a file that has never been applied (decision D5). Four read-only auditors ran in parallel (identity, dashboard, integrity, readiness); their line-level claims were re-verified by the lead before inclusion, and three were corrected.

## Verdict

No real organization can run a season on this today: a director cannot publish a schedule, cancel a practice, see who owes money, take attendance, or collect a payment from a parent who has no account, and the first screen they see after signing in shows four fabricated drafts about athletes who do not exist. The single thing most in the way is not a missing feature — it is that the live database and the repository describe two different products: the schema fixes for the staff-only model, the anonymous-read leak, the badge gate and the whole event model exist only as unapplied files while production still runs the marketplace-era rules, seeded with demo data that anyone with the publishable key can read. Until what is on `main` is applied to a database, the demo seeds are removed from the render paths, and the one true attachment path (a bearer invite token) is bound to the invitee, every downstream item in the queue — slice 2, registration, the parent channel — is being built on ground that does not hold.

## Critical — safety, minors, money, unverified claims

**C1. A real organization is readable with no session, live.**
*Where:* live policy `providers_select_public USING (status = 'approved')` (baseline.sql:4674) plus anon column grants (baseline.sql:4780).
*Evidence:* `GET /rest/v1/providers?select=id,business_name,status,location,sports,background_check_status&limit=5` with only the publishable key → `200`, `[{"business_name":"Rivertown FC","status":"approved",…}]` (2026-09-16). Live `information_schema.role_table_grants` shows anon holds SELECT on **41** public tables — `athletes, team_athletes, guardian_links, installments, fee_schedules, sessions, profiles, waiver_signatures, staff_certifications, settings_audit, provider_settings, billing_subscriptions, …` — every one answering `200 []` today only because RLS returns zero rows. The fix (`20260915_001065_staff_only_signup.sql:43-46`, drops the policy and revokes anon) is on `main` **as a file**.
*Consequence:* the wedge in 20.5 ("no unauthenticated route that touches org data") is false in production; the first org name, sport and location is public; 40 more tables are one permissive policy away from the same.
*Also:* my own guard `tools/check-anon-surface.mjs` (merged in #24) reported "no anonymous read path" during this audit because it probes `select=*`, which trips a column-level 42501 and masks the leak — a false negative in the very tool meant to catch this. Fix size: one line (probe granted columns).
*Fix size:* apply 001065 (minutes) + fix the probe (one line).

## Incoherent — the dashboard walk-through

Rendered headless with a verified provider, an approved org and empty collections (Audit B; the two load-bearing claims re-verified at the lines by the lead). The rail (`host:10992-10999`) is eleven tabs; every signed-in user gets the same eleven regardless of role.

- **Queue** is the first screen. It shows four fabricated drafts (C4). A director who has never imported anyone reads "3 athletes missing a signed waiver — Nia O., Marcus B." and either believes it or stops trusting the product on screen one.
