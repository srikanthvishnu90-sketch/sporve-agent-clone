# Incident 2026-10-22 — coach assistant answers 429 and fails hard

Status: root-caused; fix on branch `fix/assistant-reliability` (repo only — the
two edge functions still need a deploy, see "Owner steps").

## Verdict

**(c) the plan quota.** Not the model provider, not the burst limiter.

The coach's org is on the Free plan. Production `plan_entitlements.ai_monthly_quota`
for `free` is **3**, and `ai-gateway` counts every model call (not every Ask
message) against it. The org made 3 calls on 2026-10-19; every call after that
was refused by the gateway's monthly budget check with **HTTP 429**. `coach-command`
then relabelled that 429 as "AI request limit reached. Please try again shortly."
and the client showed "the assistant call failed". The coach was told to retry
something that could not succeed until 1 November.

Three defects stacked:

1. Plan quota returned 429 instead of 402 — breaks CONTEXT I3.
   `supabase/functions/ai-gateway/index.ts` (pre-fix lines 548-559).
2. `coach-command` turned every gateway 429 into "try again shortly".
   `supabase/functions/coach-command/index.ts` (pre-fix line 1676).
3. The client ignored the status entirely and printed one generic failure.
   `src/sporve-web.host.html` `askCoach()` `.catch(()=>…)` (pre-fix ~line 20947).

## Fix (this branch)

Server — `supabase/functions/ai-gateway/index.ts`
- Plan quota and spend cap now return **402** with the I3 payload
  `{ reason, current_plan, upgrade_to, limit, current }`. The spend cap uses
  whole cents (`unit: "usd_cents"`) so `limit` and `current` stay integers.
- The Anthropic call is wrapped in a bounded retry. It retries 408/429/500/502/503/504/529
  and network resets, at most 3 attempts. Backoff is exponential with full jitter
  (base 500 ms, cap 4 s), and the provider's `retry-after` header wins over the
  computed delay. The total time budget is 12 s. The retry is safe because the model
  call has no side effects: the gateway still writes exactly one audit row per request.
  The helper lives in `supabase/functions/_shared/upstream-retry.mjs` and is
  mirrored inline in the gateway, so the deployed artifact stays one flat file.
- If the provider is still busy after the retries, the gateway returns
  **503** `{ reason: "upstream_busy", retry_after }` + `Retry-After`. Other
  provider failures stay 502.
- The burst limiter stays a 429. It now sends `reason: "rate_limited"`,
  `retry_after` (seconds until the window resets), and a `Retry-After` header.

Server — `supabase/functions/coach-command/index.ts`
- Passes 402, 429 and 503 through with their payloads instead of relabelling them.
- The "deliver, don't clarify" retry turn only replaces the first answer when it
  succeeds. Before this change, a quota or busy refusal on that retry discarded
  a complete answer.

Server — `supabase/functions/agent-intake/index.ts`
- One line: it stops its AI loop on 402 as it already did on 429. This keeps the
  nightly intake run from looping on the new status code.

Client — `src/sporve-web.host.html` (`askCoach`), `src/mod-api.js`
- API errors now carry the parsed body and the `Retry-After` value.
- A bare 401 from an edge function now triggers the existing one-time token
  refresh. Before, only PostgREST error codes did, so an hour-old tab failed.
- The client retries once automatically, and only on 503, or on 429 when
  `retry_after` is 8 s or less. The server refuses both before any draft is
  queued, so the retry cannot double anything. During the wait, the thinking
  bubble shows "Still working, retrying".
- The error copy now names the failure. Plan allowance: no Try again, a
  "See plans" button that opens Billing. Busy, rate-limited, signed out,
  offline and timeout each get their own line. Every case except plan
  allowance keeps the `data-airetry` "Try again" button.

## Proposed limits (data change — owner decides; not applied)

The Free row contradicts the build constitution. CONTEXT §6.1 says Free gets
**25 Ask messages/month**, and `plan_entitlements.ask_quota_month` already says 25.
But the gateway enforces `ai_monthly_quota = 3`, and it counts model **calls**,
not Ask messages. One coach turn makes 1 to 5 calls: the turn itself, plus a
truncation retry, a deliver-don't-clarify retry, and the draft writer and its retry.
So a Free coach gets between 1 and 3 questions a month. That is too tight for a
coach to see the product work, and it is not what the pricing table promises.

Proposal: set Free `ai_monthly_quota` to **75**, which is 25 Ask messages × up
to 3 calls each, and keep the $1.00 spend cap as the margin backstop. Measured
cost is $0.0039 per Haiku call (this month's 3 calls cost $0.0117), so $1.00
covers about 250 calls. The cap, not the count, protects the margin.
Leave Pro and Enterprise unchanged. The minute (20) and day (300) burst limits
are fine: real use peaked at 2 calls a minute.

Longer term, count Ask **turns** rather than gateway calls. One option is a
per-turn id that coach-command forwards, which the gateway counts once.
Without it, the constitution's 25 cannot be honoured exactly.

To apply the number change (CONTEXT 6.2: "changing a limit is a data change,
never a code change"), run this in the Supabase SQL editor for project
`aveqjeafghmwafkbbnor`:

```sql
update public.plan_entitlements set ai_monthly_quota = 75, updated_at = now() where plan = 'free';
```
